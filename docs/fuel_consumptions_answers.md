# Контрольные вопросы ЛР2

## Виды баз данных

Реляционная БД хранит данные в таблицах со строками, столбцами и ограничениями. PostgreSQL в нашей работе — реляционная СУБД. Связи задаются первичными и внешними ключами. Нереляционные БД включают документные, ключ–значение, графовые и колоночные хранилища. MinIO — объектное хранилище файлов, а не замена реляционной БД приложения. SQL-БД удобна здесь, потому что карточки, пользователи и лайки имеют фиксированные поля и связи.

## SQL запросы

SELECT читает данные, INSERT создаёт строки, UPDATE меняет их, DELETE физически удаляет. CREATE TABLE создаёт схему, ALTER TABLE меняет её. WHERE ограничивает строки, ORDER BY задаёт порядок, LIMIT ограничивает количество, COUNT считает строки. JOIN соединяет таблицы. В приложении поиск использует условия статуса и расхода BETWEEN, а получение ленты — LIMIT 1. Логическое удаление выполняет UPDATE статуса. Значения передаются параметрами, а не склеиваются с SQL; это защищает запросы от SQL-инъекции.

## Курсор и прямой SQL

Курсор позволяет последовательно читать набор строк результата запроса. В Go `database/sql` метод QueryContext возвращает `Rows`; для чтения вызывают Next и Scan, затем Close и Err. Для UPDATE без возвращаемых строк применяется ExecContext, который возвращает Result и число изменённых строк через RowsAffected. В нашей ЛР2 прямой UPDATE удаления выполняется именно через ExecContext. Мы не используем SQL-команду DECLARE CURSOR для UPDATE: у него нет читаемого набора строк. Это реализация требования удалить без ORM через прямой SQL.

## ORM

ORM сопоставляет объекты языка с таблицами базы данных и генерирует SQL. В работе используется GORM. Go-структуры — модели, поля и column-теги соответствуют столбцам. Create генерирует INSERT, Updates — UPDATE, First — SELECT с LIMIT 1, Where задаёт условия, Find читает набор записей. ORM упрощает обычные операции, но не заменяет понимание SQL и ограничений БД. Пять контроллеров обращаются к БД через GORM; удаление выполнено отдельно через database/sql.

## Модель

Модель описывает структуру и смысл данных предметной области. FuelConsumption — карточка расхода топлива: название, описание, статус, URL медиа, расход, бак, автор и даты. FuelConsumptionDriver — пользователь-водитель. FuelConsumptionLike — строка связи водителя и карточки. Модель не является самой БД: Go-структура существует в приложении, а PostgreSQL хранит строки и обеспечивает ограничения независимо от процесса Go.

## Миграция

Миграция — управляемое изменение схемы БД: создание таблиц, ключей, индексов и ограничений. В работе схема описана в версионированном файле 001_schema.sql, который применяет отдельная программа cmd/migrate в транзакции. Повторный запуск CREATE IF NOT EXISTS не удаляет данные. Начальное заполнение — отдельный 002_seed.sql, его можно выполнить через Adminer. Оно отличается от миграции: схема описывает структуру, seed добавляет учебные строки. Если позже меняется схема, нужно добавить новую миграцию, а не считать IF NOT EXISTS механизмом изменения существующих столбцов.

## Первичный и внешний ключи

Первичный ключ уникально определяет запись. В каждой из трёх таблиц есть отдельный BIGINT ID. Внешний ключ ограничивает ссылки существующими родительскими строками. Карточка ссылается на автора; лайк — на карточку и водителя. Связь многие-ко-многим разбивается на две связи один-ко-многим с таблицей лайков. Логин и пара водитель–карточка уникальны. Все внешние ключи имеют ON DELETE RESTRICT; каскадное удаление запрещено.

## Черновик и транзакции

У каждого пользователя не более одной карточки со статусом «черновик». Это гарантируется частичным уникальным индексом по автору с условием статуса. Простого SELECT перед INSERT недостаточно: два одновременных запроса могли бы оба увидеть отсутствие черновика. Ограничение БД не позволяет такому состоянию возникнуть. Транзакция объединяет операции в атомарный блок: COMMIT фиксирует их, ROLLBACK отменяет. Свойства ACID: атомарность, согласованность, изоляция, долговечность. Миграция выполняется в транзакции, а публикация карточки меняет все поля одним UPDATE.

## Чистая архитектура

Идея чистой архитектуры — отделить бизнес-правила от деталей ввода-вывода: HTTP, СУБД, интерфейса. Зависимости направляются к бизнес-логике, внешние адаптеры реализуют её интерфейсы. В учебном проекте отделены модели, репозиторий, HTTP-контроллеры и шаблоны. Это разделение ответственности, но не полный канонический вариант чистой архитектуры: контроллер зависит от конкретного GORM-репозитория. Для дальнейшего развития можно вынести сценарии создания/публикации в отдельный слой и зависеть от интерфейса репозитория, а GORM оставить внешним адаптером. На защите не нужно называть текущую учебную структуру полноценной чистой архитектурой.
